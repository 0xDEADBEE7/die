# Using DIE

How to install and run DIE, and every key and command it has on `m0/integration`, read from the binding tables in `crates/die-vim/src`, `crates/die-core/src` and `apps/die-dev/src/lib.rs`. Keys follow your Evil in fundamental-mode unless [m0-log.md](m0-log.md) says otherwise. `\hk` tells you what any key does, and `\hc` what any command does.

## Install and run

```sh
cargo xtask app          # builds ~/Applications/DIE.app from a release build
open ~/Applications/DIE.app
```

- **On a new Mac**, see [what a build needs](#what-a-build-needs) first.
- `cargo xtask app` links `~/.local/bin/die` if that directory is on your PATH. Otherwise it prints the one line to add to your shell config. It replaces a link there but never a file. `--home DIR` installs under DIR instead, to try it without touching yours.
- There is one instance. Launching it again from the Dock or Finder does nothing.
- **What it opens on:** with no file named, your [jellyfish](#jellyfish), over the one window the session brought back, and `q` lets it go; a session's splits come back as they were, with no jellyfish. `die foo.rs` opens on the file, and a restart on what was there.
- **Where it starts:** in your home directory, as Emacs.app does. LaunchServices starts an app in `/`, and DIE.app goes home from there, so the jellyfish, `*scratch*`, your status line, the first `\f` and the first `\e` are in `~/`. A launch puts `*scratch*` there whatever directory the session kept for it, with its text as it was, and the jellyfish there whatever buffer it covers. Every other buffer comes back where it was, and so does `*scratch*` after a restart, which isn't a launch. A buffer you make takes the directory of the one you're in, as in Emacs.
- **After changing DIE or your config:** `:rebuild` in DIE. It runs `cargo xtask app` in the checkout this DIE.app was installed from, whatever file you're in, with cargo's output in `*rebuild*` below. To build another checkout, run `cargo xtask app` there once, and `:rebuild` builds that one from then on. If it builds, DIE restarts into it. If not, nothing is installed, the cursor in `*rebuild*` is on the first error, and `<CR>` or `gf` on its `-->` line opens the file there, as `:cn` does from anywhere. It replaces the bundle that's running, so it refuses for one outside an `Applications` folder. A change to your config takes about 2 s. By hand it's `cargo xtask app` in a terminal, then `:restart`.
- **What a restart keeps:** your buffers, unsaved text, splits, cursors, marks, registers, macros, `.` and last search, and a `die --wait` still waits. `*grep*`, `*compilation*`, `*Shell Command Output*`, `*rebuild*` and `*Buffer List*` don't come back, though `:make`'s command does, and where it ran. Commands still running are stopped, at a restart as at quit. A new build that fails to start leaves the old instance running.
- **Quit:** `:q` on the last window, `:qa`, or Cmd-Q. Each refuses if a file is unsaved. `:qa!` doesn't. Each asks first while a program runs in a terminal, `:qa!` too.

From a terminal, `die` opens files in the running DIE and returns at once. If none is running, it starts one.

```sh
die foo.rs               # as :e would
die foo.rs:12            # line 12
die foo.rs:12:3          # line 12, character 3
die foo.rs:12:3:         # as compilers print it
die +12 'odd:name'       # the name is taken literally
die a.rs b.rs            # each opens in turn, and the last ends up on screen
die                      # brings DIE forward, or starts it
die --wait msg.txt       # returns once you're done with it (-w for short)
```

`die file:line` leaves a jump, so `C-o` comes back. `open -a DIE file`, a Finder double-click on a file DIE is the opener of, and dropping files on DIE's Dock icon open them in the running DIE too, or start it with them. A name with an accent comes as you'd type it, so `:b café` finds it. DIE's Info.plist says it can edit any file, at the rank that makes it the opener of none, so Finder should list it in Open With, and Get Info, then Open with, then Change All should make it the opener of every file of that kind. Only `open -a` has been tried: neither Finder's list nor a double-click has.

**DIE as git's editor.** `die --wait` opens files as `die` does, then waits until you're done with them, as `emacsclient` does. git runs `$EDITOR` through a shell, so the flag works there. In your shell's startup file:

```sh
export EDITOR="die --wait"
```

Or for git alone, `git config --global core.editor "die --wait"`.

- **Done** is `:wq`, `:x` or `ZZ`, which save first, or `:q`, `ZQ` or `C-w q`, which refuse while it has unsaved changes, as `:q` does. `:q!` drops them. Killing the buffer is done too: `:bd`, `:kill-buffer`, or the Buffer List's `x`. In a split these finish the file and leave the window open. `C-w c` only closes the window.
- **`:cq` gives up** on the file: `die --wait` returns 1, so git stops the commit or the rebase, and the file goes as with `:q!`, with what you typed. On a file nothing waits on, `:cq` says "This buffer has no clients" and does nothing.
- **Then** a buffer made for `die --wait` goes, unsaved text and all, and its window shows what any window shows after a kill: the buffer you used last that no window shows. Your Emacs's `server-edit` goes back to what that window showed, which is the same unless another window shows it. A file that was open before `die --wait` stays open and on screen, and goes last in the buffer list. `die --wait a b` shows `b`. Done with it, `a` comes up, and it returns once both are done. `:q!` and `:cq` bring nothing up and say nothing, as your Evil's `:q!` runs only `server-buffer-done`. Several can wait at once, each for its own files.
- **It returns 0** once you're done, so a commit message left as git wrote it aborts the commit, as git decides. It returns 1 after `:cq`, if none of its files would open, or if DIE quits or crashes before you're done, so that git stops rather than go on with a message or a rebase's list saved half done. That's where it differs from `emacsclient`, which returns 0 when Emacs goes. A restart (`:rebuild`, `:restart`) hands it to the new DIE, which waits on its files as they were. With no DIE running it starts one and waits, and while DIE is starting or restarting it waits up to 15 s for it.

### What a build needs

- **The Xcode Command Line Tools** (`xcode-select --install`), for git and the linker.
- **Rust through [rustup](https://rustup.rs).** The first cargo command in the checkout installs the Rust that `rust-toolchain.toml` pins, 1.96.0 now, with rustfmt, clippy and the std for x86_64 and aarch64 Linux, which the checks use.
- **The crates.** The first build fetches the ones `Cargo.lock` names from crates.io, and libghostty-rs from GitHub at the rev `Cargo.toml` pins. The terminal's engine, built for Apple silicon, is in the checkout, under `crates/die-term-sys/vendor`, so nothing builds or fetches it.
- **The fonts.** `cargo xtask app` fetches Ioskeley Mono Term from GitHub into `fonts/` when it isn't there, and checks each file by SHA-256. `cargo xtask fonts` does only that. You can copy `fonts/` from another checkout instead: a file whose checksum doesn't match stops the build.

**Where rustup can't fetch the pinned Rust**, as on a network that blocks static.rust-lang.org:

- Point rustup at a mirror your network allows with `RUSTUP_DIST_SERVER`, and `RUSTUP_UPDATE_ROOT` for rustup's own updates, or at its proxy with `HTTPS_PROXY`, which cargo and the fonts' download follow too. Then the pin installs as above.
- Or build with a Rust you have, if it's at least `Cargo.toml`'s `rust-version`, 1.95 now (`cargo xtask msrv` checks that DIE builds with it). In the checkout:

  ```sh
  rustup toolchain list         # what you have, such as 1.95.0-aarch64-apple-darwin
  rustup override set 1.95.0    # a name from that list: any other is a download
  cargo xtask app
  ```

  rustup takes a directory's override over its `rust-toolchain.toml`, and `cargo +1.96.0` or `RUSTUP_TOOLCHAIN` over both. So `cargo xtask app` and `:rebuild` build with 1.95.0, and no tracked file changes. The override takes nothing from `rust-toolchain.toml`, so rustup fetches no rustfmt, clippy or Linux std either. `rustup override unset` in the checkout goes back to the pin.
- The checks (`cargo fmt`, `cargo xtask budget`, `cross-check` and `ci`) are meant for the pin. Another rustfmt can format, and so count, differently, and cross-check needs the Linux std.
- With a Rust that isn't from rustup, nothing reads `rust-toolchain.toml`. Cargo only refuses a Rust older than `rust-version`.

## DIE's own keys

The leader is `\`, in normal state.

| Key | Command | What it does |
|---|---|---|
| `\\` | `find-file-home` | Fuzzy find any file under your home |
| `\p` | `find-file-project` | Fuzzy find under the nearest parent with `.git` |
| `\f` | `find-file` | Find a file, going down from the buffer's directory |
| `\/`, `\]` | `switch-buffer` | Switch buffer |
| `\}`, `\?` | `buffer-menu` | The Buffer List, to show, save and kill buffers |
| `\r` | `grep` | Search the project |
| `\x`, `M-x` | `command-palette` | Run any command by name, recent first. `M-x` works in insert and visual too |
| `M-!` | `shell-command` | Run a shell command, as `:!` does. It works in insert and visual too |
| `\z` | `toggle-max-width` | Turn the 80-column centered text on or off, in a file or a terminal. The prompts, their lists and the messages keep to its margins, from where the line numbers start, under a status line that runs edge to edge |
| `\hk` | `describe-key` | What a key does |
| `\hc` | `describe-command` | What a command does |
| `\e`, `:term`, `:terminal` | `term` | Open a new [terminal](#terminal) in this window, as your `termin-open` does |
| `\g` | `term-switch` | Go to `*terminal*`, or open it, as your `ghostel` does |
| `\o` | `orchid` | orchid's session browser, as your emacs-orchid-client's `orchid`: see [orchid](#orchid) |
| Cmd-Q | `quit` | Quit, in every state. It asks first while a program runs in a terminal |
| Cmd-V in a terminal | `surface-paste` | Paste the clipboard into the program, as one piece it sees bracketed, or `"` if the clipboard has no text |

`:name` runs any command by name, so also `:restart`, `:kill-buffer`, `:quit`. While you type the name, `:` lists commands as `M-x` does: see [Prompts](#prompts).

**The finders** list files while you type. They skip `.git`, `target`, `Library`, `.cargo/registry`, `.claude/worktrees` and a fixed set of others, and they don't read `.gitignore`. Only the best 1,000 matches can be reached.

**`:grep PATTERN [DIR]`**, or `\r`. Searches with `/`'s smartcase regex, on a background thread, into `*grep*`, with focus staying where it was. One row per line. It stops at 10,000 rows, and skips binary files and files over 10 MB. If the last word names a directory, that's the root, so `:grep mod tests` searches for `mod` in `tests/`.
- `<CR>` on a row opens it in another window.
- `:cn`, `:cp` go to the next and previous result, from any window.
- `gf` and `gF` open `path:line:col`, `path:line`, `path(line)` or `path(line,col)` under the cursor, trying the buffer's directory and then the project root. `]f [f ]F [F` do the same. `gf` in Visual takes the selection as the name.

**The Buffer List**, `\}`, `\?`, `:ls` or `:buffers`, shows `*Buffer List*` in this window, as your Emacs's `buffer-menu` does. `:files`, or a count first, lists only buffers with files. A row per buffer, the one used last first, leaving out the menu and names starting with a space. Its columns are Emacs's: `C` is `.` for the buffer you came from, `>` for one marked to show, `D` to kill; `R` is `%` for read-only; `M` is `*` for unsaved changes, `S` to save; then the name, the size in characters, the mode (Fundamental, as DIE has no major modes yet) and the file. A line break in a name or a path shows as `^J`. The titles are its first line. Evil's keys work there, except these, which are evil-collection's:

- `d` and `C-k` mark the line's buffer to kill and move down, `C-d` moving up, a count marking that many. `s` marks it to save and `m` to show, each moving down.
- `u` takes the line's marks off and moves down, or up with a count. `<Del>` moves up and takes that line's off. `U` takes every mark off.
- `x` saves what's marked `S` and kills what's marked `D`, asking as `:kill-buffer` does when that loses changes to a file. `no` keeps that one and goes on, `Esc` stops there.
- `~` marks the buffer as having no unsaved changes, or with a count as having some. `%` turns its read-only on or off.
- `go` and `<CR>` show the buffer in this window, `gO` in another (a split if this one is alone), `1` alone, `2` with the buffer before it above, and `gv` alone with each one marked `>` in a window below, sized as Emacs sizes them. When they'd leave a window no row of text, `gv` does nothing.
- `o` and `S` sort by the column under the cursor, or by a count's column from 0 (`3o` by name), and the other way when pressed again. `T` lists only buffers with files, or all of them again. `gr` lists the buffers again. `X` puts the buffer last in the buffer list, and its row at the end.
- `q` and `ZZ` show what the window showed before and put the menu last. `ZQ` closes the window, as elsewhere.
- `1` and `2` aren't counts there, but after a count's first digit they're digits of it, so `31d` marks 31 rows. `gg` goes to the titles.
- Evil's insert and edit keys do nothing there, as your evil-collection makes them in a read-only list: `i I a A c C D r O p P J = < >`.

## Running commands

Commands run without a terminal, with your `$SHELL`, in the buffer's directory, as Emacs runs them. They get the PATH your login shell sets, asked once each time DIE starts, with `~/.local/bin` and `~/.cargo/bin` first if it hasn't got them, so DIE.app from the Dock finds cargo and git as your terminal does.

**`:make cargo test`**, or `M-x compile`. The command's output and errors stream into `*compilation*` below as they come, a line before its newline too, with the focus staying where it was, under Emacs's header: the `-*- mode: compilation; default-directory: ... -*-` line, `Compilation started at ...` and the command. Its last line is Emacs's, `Compilation finished at ..., duration 4.56 s` or `Compilation exited abnormally with code 101 ...`, and the command row says it too.
- `M-x compile` asks with the last command on the line (`make -k ` the first time), and `<Up>` for older ones. `:make` alone, `M-x recompile`, and `gr` in `*compilation*` run the last one again, where it ran, after a restart too.
- Files with unsaved changes are offered for saving first, one at a time: `y` saves it, `n` doesn't, `!` saves the rest, `q` saves no more, and `Esc` runs nothing.
- One runs at a time. Another asks whether to stop the one running. `C-c C-k` in `*compilation*`, or `M-x kill-compilation`, stops it as Ctrl-C would. Quitting DIE, or a restart, stops it without asking: a hangup, then a kill if it's still there.
- `<CR>` on an error's line opens the file there, in another window, and `gf` on its path opens it in this one. `:cn` and `:cp` go through the errors from any window, as they go through `*grep*`'s rows: whichever you made or went to last. In `*compilation*`, `gj` `gk`, `C-j` `C-k` and `<Tab>` `<S-Tab>` move to the next and previous error's line.
- An error is rustc's and cargo's `--> path:line:col`, a test's `panicked at path:line:col:`, or `path:line:col: message` and `path:line: message`. `:cn` passes over notes: a `-->` under a `note:` or `help:` line, any `-->` after an error's first, and `:::` lines, which point at what explains the error, as std's source or a struct's definition. `<CR>` on one opens it.
- rustc's paths, and a test's, are read from the cargo workspace's root first, since cargo names files from there wherever it runs, then from the directory the command ran in, then from its project (`.git`). `path:line:` lines are read from the directory it ran in first. A path that's in none of them says "Can't find PATH from DIR".
- A carriage return with more of its line after it wipes the line, as in Emacs, so a progress line shows its last state.
- Output past 8 MiB is cut, with a note saying so, and the command runs on.

**`:!cmd`**, or `M-!`. Runs a shell command, and shows one line of what it prints on the command row, or more in `*Shell Command Output*` below. With nothing printed, it says whether it succeeded. In the command, `%` is the buffer's file and `#` the other buffer's, `\%` and `\#` themselves. `:!!` runs the last one again.
- **`:{range}!cmd`** sends the lines to the command and puts what it prints, errors too, in their place, as one change: `:%!sort`, `:'<,'>!jq .`, `:.!tr a-z A-Z`. Output with no newline at its end runs into the next line, as in your Evil.
- **The `!` operator** opens `:` with its lines and a `!`: `!!` for this line, `!ip`, `!G`, or `!` over a selection.
- **`:r !cmd`** puts what the command prints below the cursor's line, or the range's last, and `:0r !cmd` above the first. `:r file` does the same with a file's text.
- A key after a command waits up to half a second for it, so a macro with `:%!sort` works on the sorted lines. A slower one goes on in the background and its output comes when it's done, or it's stopped when DIE quits. If you changed the text meanwhile, a filter leaves it alone and says so. A command that prints more than 8 MiB is stopped. A filter or `:r !` whose output isn't UTF-8 leaves the text alone too, and says so.

## Prompts

These work on `:`, `/`, `?` and the finders.

| Keys | What they do |
|---|---|
| `<CR>` / `<Esc>` `C-g` `C-c` | Answer / cancel |
| Cmd-V | Paste the clipboard, without its final newlines |
| `C-y` | Paste the newest kill |
| `C-r x` | Paste register x |
| `C-r C-w`, `C-a`, `C-o`, `C-f`, `C-l` | Paste the word, WORD, symbol, file name or line under the cursor |
| `<Left>` `C-b`, `<Right>` `C-f`, `<Home>` `C-a`, `<End>` `C-e` | Move |
| `M-b`, `M-f`, also `C-` or `S-` with the arrows | Move by word |
| `<BS>` `C-h`, `<Del>` `C-d`, `C-w` `M-BS`, `M-d` | Delete a character, a word |
| `C-u`, `C-k` | Delete to the line's start, to its end |

On `:`, `/` and `?` only: `C-v` inserts the next key literally, `<Up>` `<Down>` recall history matching what's typed, `C-b` goes to the start, and `C-u` deletes the whole line. `C-p` `C-n` also go through history. On `:` they do beside its list too, as below.

**`:`'s list.** While the line is a command's name, after any range (`%`, `'<,'>`, `2,5`), `:` shows a list like `M-x`'s, flex matched against the name: the ex commands under their whole names (`write`, `quit`, `substitute`, `vsplit`, `nohlsearch`) and every other command. With nothing typed, the ones you ran from `:` come first. Once you type, the top row is the command the name runs, as Vim reads a short name (`quit` for `q`, `substitute` for `s`, `display` for `di`), then the names it starts, then the others that match.

| Keys | What they do on `:` |
|---|---|
| `<CR>` | Run the line as typed, so `:w` writes. Once you've moved to a row, run that row, with the range kept, which a command that takes none ignores |
| `<Down>` `C-n`, `<PageDown>`, `M-<` `M->` | Move in the list. No row is chosen until you do |
| `<Up>` `C-p`, `<PageUp>` | From the line, history as in Vim, so `:<Up>` brings back the last line and `:s<Up>` the last `:s`. In the list, move up, and from the first row back to the line |
| `<Tab>` | Put the chosen row, or else the top one, in place of the name, with nothing after it |
| `M-p` `M-n` | History, list or not |

Once you're in the history, all of these that walk it stay there until you change the line, so `C-p` `C-n` go back and forth as in Vim, though a line there is a name with a list. Once anything follows the name (a space, a `!`, or `/` after `s`), the list goes, and its rows: the line moves to the bottom row, as Vim's is, and the keys are as above.

In `\f`, `<S-Tab>` goes up a directory: a name you've half typed goes first, then the directory on the line, and from `~/` it goes to `/Users/`.

On a list of candidates: `<Down>` `C-n` and `<Up>` `C-p` choose a row, `<PageDown>` `C-v` and `<PageUp>` `M-v` go a screenful, `M-<` and `M->` go to the ends, `<Tab>` puts the row on the line, `M-<CR>` answers with what's typed, and `M-p` `M-n` go through history.

## Changing

- **Insert:** `i a I A o O gi`. Replace: `R`.
- **Operators:** `d c y < > = g~ gu gU`, doubled for lines, with any motion or object.
- **Short forms:** `x X s S D C Y ~ r J gJ`, `p P`, `u C-r` (also `:u`), `.`.
- **Objects:** `iw aw iW aW io ao` (word, WORD, symbol: `cio` for snake_case), `ip ap`, `i" a" i' a'`, ``i` a` ``, `i( a( ib ab`, `i[ a[`, `i{ a{ iB aB`, `i< a<`.
- **Registers:** `"x` then a command. `a-z`, `A-Z` to append, `0`, `1-9`, `-`, `_`, `+` the clipboard, and read-only `.`, `:`, `/`, `%`. Every kill also goes to the clipboard, as in your Emacs. `:reg` (`:registers`, `:di`, `:display`) lists them all in `*registers*` below, a macro as its keys, and `:reg ab` only `a` and `b`. `:q` closes it.
- **Macros:** `q{x}` records into `x`, `q{X}` adds to it, and `q` stops. While it records, the bottom row's right end says `recording @x`, and stopping says `Recorded @x` (or `Added to @x`). `@x` plays it, `@@` plays the last again, `@:` runs the last ex line, each with a count. A macro can be edited as text: `"xp`, change it, `0"xy$`. A typed `C-g` stops a running macro, or a `:norm`.
- **On each line:** `:norm keys` (`:normal`, `:norm!`) types the keys on each line of a range, from the line's start, the cursor's line if none is given: `:%norm A;`, `:'<,'>norm @q`, `:5,$norm .`. A line whose keys fail is left quietly and the next goes ahead, and a macro or `:norm` that ran the `:norm` goes on after it. One `u` undoes it all. Each character is a key, so put an Esc or Enter in with `C-v` first. A prompt the keys leave open is answered as it stands, as in your Evil, so `:%norm :s/a/b/` runs the `:s` on each line. `:g/pat/cmd` runs an ex command on each line that matches, and `:g!` and `:v` on each that doesn't, the whole file if no range is given: `:g/TODO/norm @q`, `:v/^$/norm A;`. Any delimiter works, an empty pattern is the last search, and the pattern becomes the last search. It needs a command: there's no `:p`. The commands on lines below work there too: `:g/TODO/d`, `:v/./d` to drop blank lines, `:g/^/m0` to reverse the file, `:g/fn /t$` to copy every `fn` line to the end. `:g/pat/d` alone, with nothing after the `d`, deletes them all at once into no register, and leaves the last search as it was, as in your Evil. One `u` undoes any `:g`.
- **Lines:** each takes a range (`%`, `'<,'>`, `N,M`, `.`, `$`, `'x`, `+n`, `-n`, or a count before `:`), the cursor's line if none is given, and is one `u`. A range's line 0 is line 1, as in Vim, except that `:0r` reads above it. None is what `.` repeats, as in your Evil, and `@:` runs it again.
  - `:d [x] [count]` (`:delete`) deletes the lines into register `x` or the kill ring, as `dd` does. A count takes that many lines from the range's last, so `:d 3` and `:d a 3` work, and `:d3` too. `:y [x] [count]` (`:yank`) yanks them the same way. After a range, `:y` leaves the cursor where it was, or at the selection's start if you typed `:` in visual state.
  - `:pu [x]` (`:put`) puts register `x`, or the newest kill, as whole lines below the range's last line, whatever the register holds. `:pu!` puts them above. The cursor goes to the first non-blank of the last line put.
  - `:m {address}` (`:move`) moves the lines after that line: `:m0` to the top, `:m$` to the end, `:m+1`, `:m-2`, `:m'a`. `:t {address}` and `:co[py]` copy them there: `:t.` duplicates the line, `:t$` copies it to the end. The cursor goes to the last line moved or copied. Moved to where they are, nothing moves, and a range given leaves the cursor at its start.
  - `:j[oin] [count]` joins the lines as `J` does, `:j!` as `gJ` does, and a count joins that many from the range's last.
  - `:>` and `:<` shift the lines once, as `>>` and `<<` do. Your Evil ignores a count there, and `:>>` and `:<<` are no commands in it, so neither is here.
  - `:sor[t]` sorts the lines, the whole file if no range is given, `:sort!` the other way, ties keeping their order. Flags: `i` ignores case, `u` keeps one of lines that are the same, `n` sorts by the first decimal number, `x` by the first hexadecimal one, `o` octal, `b` binary, a line with no number coming first (before any number down to your Emacs's `most-negative-fixnum`, as there). `:sort /pat/` sorts by what follows the first match, and with `r` by the match itself; a line it doesn't match sorts first. The pattern is Rust's regex and always ignores case, as Emacs's sort does. `:sort //` is a plain sort: your Evil doesn't see `/`'s last search there.
- **Substitute:** `:s/a/b/`, with flags `g` and `&`, `~` for the last replacement, ranges `%`, `'<,'>`, `N,M`, `.`, `$`, `'x`, `+n`, `-n`. A count before `:` starts the line with that many lines from the cursor's, so `3:` is `:.,.+2`. `&` repeats it on the line, `g&` everywhere, also `:&`, `:&&`, and `:s` alone.

## Selecting

`v V C-v`, `gv` to reselect. Motions, objects and operators work, plus `o` and `O` for the other end, `I` and `A` to insert on each line, `u` and `U` for case, `R` and `X` for whole lines, `r`, `J`, `p`, `&`, `:`, and `gf`.

## Windows and buffers

- **`C-w` then:** `h j k l` and arrows, `w W t b p` to move; `s S v n` to split; `c q o` to close; `= + - > < _ |` to size; `H J K L` to move the window; `r R x` to rotate and exchange; `:` for ex; digits for a count. A key with Control does the same, as `C-w C-h`.
- **Ex:** `:sp[lit]`, `:vs[plit]`, `:new`, `:vne[w]`, each with a file; `:clo[se]`, `:on[ly]`. Every ex command takes Vim's short forms, as `:wri`, `:bdel`, `:nohls`, `:sub/a/b/`.
- **Buffers:** `:e file`, `:e!`, `:b name`, `:bn`, `:bp`, `C-^`, `:bd`, `:bw` (`!` to drop unsaved text), `:kill-buffer`. `:bn` and `:bp` go through file buffers. `:ls` (or `:buffers`) opens [the Buffer List](#dies-own-keys), and `:files` the same with only buffers with files.
- **Files:** `:w`, `:w!` over a file changed on disk, `:up`, `:wa`, `:q`, `:q!`, `:wq`, `:x`, `:wqa`, `:xa`, `:qa`, `ZZ`, `ZQ`, and `:cq` on a file `die --wait` waits on. Files changed on disk reload by themselves if you have no unsaved text there, and `:w` refuses if you have. On a file `die --wait` waits on, `:q` and the rest finish it rather than close the window or quit: see [DIE as git's editor](#install-and-run).
- **Saving elsewhere:** `:w path` from a buffer with no file, such as `:new`'s, saves it there, and the buffer then visits that file. From a buffer with a file it writes a copy, and the buffer keeps its file and its unsaved changes, as in your Evil. `:sav[eas] path` saves and moves the buffer to the new file. A path is taken from the buffer's directory, as `:e` takes it, and `~/` is your home. A file that's already there is written over only with `!` (`:w! path`, `:saveas! path`). `:wq path` and `:x path` write there, then close.
- **Which file:** `:f` (`:file`) and `C-g` say the file's full path, its lines and how far down the cursor is, as your Evil's `:f` does. The status line shows only the directory. `C-g` is Vim's: your Evil's quits.

## Terminal

`\e`, `:term`, `:terminal` or `M-x term` opens a terminal in this window, in the buffer's directory: `/bin/bash`, as your Emacs's `ghostel-shell` and `vterm-shell` have it, interactive and not a login shell, as vterm (and so your `termin-open`) starts it, so it reads your `~/.bashrc`, whose prompt and PATH additions go on the login PATH DIE works out. DIE's default, for a config that sets no shell, is `$SHELL` as a login shell. `:term cmd`, as `:term top`, runs `cmd` through that shell instead (`/bin/bash -c cmd`), as Vim's `:terminal cmd` does. The first is `*terminal*`, the next `*terminal*<2>`, and so on. `\g` (`term-switch`) goes to `*terminal*`, or opens it if it isn't there, as your `ghostel` does. The status line shows the terminal's directory, then the program's title or the buffer's name, and `<I>` or `<N>` at the right. bash and zsh report each `cd`; sh and a login bash don't yet, so theirs is the directory they started in. When the program exits, the buffer closes, and an exit that isn't 0 is said in the messages.

- **Insert state** (`<I>`) is where it starts, with a bar cursor on the main screen, as evil-ghostel draws it, and the program's own on the alternate screen. Every key goes to the program but Cmd's: `\`, `C-c`, `C-z`, `C-d`, `C-r`, `C-k`, `C-h`, `C-g` and Tab too, with Option as Meta and the kitty keyboard flags for programs that ask. A Cmd key DIE doesn't bind goes nowhere. A key brings the live screen back if you'd scrolled up.
- **Esc in insert** always goes to normal state, on the alternate screen too, so Esc Esc interrupts Claude Code, its fullscreen mode included, and leaves vim's insert mode: the first Esc leaves insert, and normal state's sends the program one. That holds whatever the program asked of the terminal: the kitty keyboard flags, mouse tracking, bracketed paste. Ctrl-[ is Esc, as in your Emacs, here and in normal state. Cmd-Esc always goes to normal state. Shift-, Ctrl- and Alt-Esc always go to the program. After one Esc, what you type is DIE's: vim's `:wq` from habit says the terminal has no file, and `:q` asks before quitting DIE while a program runs, so give vim Esc Esc, or `C-c C-r` the terminal first. A key you let go after Esc, as a letter rolled over into it or the Ctrl of Ctrl-[, still has its release sent to a program that asked for releases.
- **The toggle**, `C-c C-r` in normal state or `M-x term-toggle-send-escape`, changes where insert's Esc goes in this terminal: from normal state, the default, to the program, for vim run in the terminal, so its Esc goes straight to vim and you stay in insert, and pressed again back to normal state. A count picks one, as evil-ghostel's `evil-ghostel-toggle-send-escape` does: `1 C-c C-r` is evil-ghostel's `auto` (to the program while it's on the alternate screen, as vim, less and htop are, and to normal state otherwise), `2` the program, `3` normal state. From auto, `C-c C-r` goes back to normal state. The messages say which. Cmd-Esc leaves insert whichever it is.
- **Pasting** is one piece, bracketed when the program asked (zsh, Claude Code, vim). A paste with a line break into a program that didn't ask, which could run it as a command, asks first, and the program's output goes on showing while it does.
- **The pointer** in insert state: a program that tracks the mouse (htop, `vim` with `mouse=a`) gets clicks, drags and the wheel over the terminal's columns, and a drag that goes into a margin stops at the edge. A click in a margin only focuses the window. Otherwise the wheel scrolls back through the last 10,000 lines, from a margin too, and less and man scroll on the alternate screen.
- **Size and margins:** a terminal is a file's width, 80 columns centered in your config, with blank margins either side and the status line edge to edge, and `\z` in normal state turns that on and off as in a file; the program hears the new size, and the cursor stays on its text, scrolled back too, while the terminal rewraps long lines to the new width. The terminal fits that area, in cells and pixels, as splits and resizes change it. Two windows on one terminal share it at the smaller area's size, as Emacs sizes a process, and the larger shows it at its area's top left.
- **Copying out:** a program's OSC 52 copy, as vim's `"+y` over SSH, goes on the clipboard and is your newest kill, so `p` pastes it anywhere. A working directory the shell reports (OSC 7) becomes the buffer's, so `\f` and `gf` on a relative path start there. zsh reports it at each prompt: DIE starts a login zsh with a `.zshenv` of its own (under `$TMPDIR`), which puts your `ZDOTDIR` back, reads your `.zshenv`, and adds the hook, and zsh then reads your `.zprofile`, `.zshrc` and `.zlogin` as ever. bash reports it too: DIE starts it with `--rcfile` at an rc of its own (also under `$TMPDIR`), which reads your `~/.bashrc` as bash would have, then adds a hook that keeps `$?` on a line after your `PROMPT_COMMAND` (in bash 5.1 and later, whose `PROMPT_COMMAND` can be an array, after its first element and before the rest). A bash you start inside the terminal inherits an exported `PROMPT_COMMAND` but not the hook, and finds no hook quietly. A login bash ignores `--rcfile`, so it doesn't report. Both rcs live in directories of DIE's that only you can write, and a name with `%` or a control character is reported escaped, so any directory's name comes through.
- **Restarts:** terminals don't survive `:rebuild` or `:restart` yet. A restart hangs their programs up, as quitting does, and kills what's left of the shell's own process group 300 ms later, and the restored session has no terminal. The shell hangs its jobs up too, so a job that ignores the hangup (`nohup`, or `trap '' HUP`) goes on running, as it would after closing a Terminal window. `:restart`, `:rebuild`, Cmd-Q, `:q` in the last window, `:qa`, `ZQ` and the rest ask first while a program other than the shell runs in one, with `!` too, since `!` speaks for unsaved text.

**Normal state** in a terminal is your Evil over what it shows: the scrollback and the screen, as text you can read, search and yank but not change. While a program is on the alternate screen (vim, less, btop, Claude Code's fullscreen mode), it's that screen alone, which has no scrollback. Esc from insert state goes there (Cmd-Esc if the toggle sends Esc to the program), with the cursor on the terminal's own, or after the wheel scrolled back, at the rows the wheel left showing, with the cursor on the last of them.

- [Moving](#moving) and [Selecting](#selecting) work as in a file: counts, objects, `/ ? n N * #`, marks, `v V C-v`, and `y` into registers and the clipboard, `"x` too. So do `:`, the `C-w` keys and your leader's.
- **Scrolling:** `C-d C-f C-b C-e C-y`, `zz zt zb`, `gg` and `G` go over the scrollback as over a file's lines, never lower than the live screen. `C-u` is the prefix argument there too, as in your Evil.
- **What shows** is the terminal's own cells and colors, scrolled to where you are, with the cursor, the selection and the search's matches drawn over them.
- **New output:** while the cursor is on the terminal's cursor line or below it, normal state follows the output, and a cursor on the terminal's stays on it. Move up and it holds still while the program goes on printing, though what it shows is still what `y` takes, after a `clear` too. `G` (`term-goto-cursor`) goes to the terminal's cursor, as evil-ghostel's does, so it follows again; `5G` is line 5. A program switching screens, as one leaving the alternate screen, takes you there too, since the other screen's lines aren't the ones you left. A selection, a waiting operator or a prompt holds it too, until it ends.
- **Lines are rows:** a line the program wrapped is a line per row, and the screen's empty rows below the prompt aren't lines, so `j` stops at the prompt, and so does `G` with a count past it. A resize rewraps them, `\z` or a split too, and a cursor that isn't following the output stays on its text at its column there, as do a selection and the top row.
- **Edits** (`x d c o r J` and the rest) say "Buffer is read-only", and `u` that there's nothing to undo.
- **The program's keys:** `<Esc>` sends the program one Esc and stays in normal state, as your `vterm-send-escape` binding does, so Esc Esc from insert interrupts Claude Code, on either screen. It's encoded as the program's kitty flags ask, with its release for a program that asked for releases. Unlike vterm's, more Escs with no other key between them send nothing, so Esc pressed a few times to be sure of normal state sends one; any other key, a motion too, re-arms it, and so does going back through insert. At the shell's own prompt Esc sends nothing at all, as Evil's Esc does nothing, so bash doesn't offer to "Display all 1773 possibilities". Nor does it while the terminal is in line mode, as a job that reads no keys leaves it (`sleep`, a `cargo build`, `cat`): there an Esc would only wait for the prompt, which would read it as Meta and lose your first letter. A count sends that many, at most two, and only where a lone Esc would go: `2<Esc>` is Claude Code's rewind. After a register (`"a<Esc>`) Esc only ends the prefix. A shell you start inside the terminal, as `zsh` typed at bash's prompt, is a program to DIE, so Esc reaches it, and its line editor then reads the first key you type after `i` as Meta, as bash did. The other way round, a program in the shell's own process group, as `fzf` in `cd $(fzf --height 40%)`, looks like the shell at its prompt, so normal state's Esc doesn't reach it; `C-c C-r` sends insert's Esc to it. `i a I A` go back to insert, at the live screen. `p P` and Cmd-V paste into the program, the clipboard or `"x`, and with a count, as `"a3p`, that many times. `C-c C-c` sends the program C-c, as your ghostel's does in every input mode, so it interrupts a job or Claude Code without going back to insert; `C-c C-z`, `C-c C-\` and `C-c C-d` send C-z, C-\ and C-d. `C-c C-r` is the toggle above.
- **The mouse** is a file's: a click moves the cursor (in a margin, to the row's start or end), a drag selects, the wheel scrolls the scrollback. The program hears no click or drag in normal state. A program that tracks the mouse (Claude Code's fullscreen mode, htop) still gets the wheel, as in insert and as your ghostel sends it in every Evil state, since its screen has no scrollback to scroll.

## orchid

`\o`, or `M-x orchid`, is your emacs-orchid-client, ported as die-orchid-client: an extension DIE builds beside itself, outside the product (scope D14), which your config registers. It drives orchid 0.2.2, your agent CLI, as Emacs does: `orchid` on the PATH your login shell sets (so `~/.local/bin/orchid` from DIE.app too), on orchid's own root, `$ORCHID_CONFIG` or else `~/.config/orchid`, passed to every command as `--config`. Its commands never inherit `ORCHID_SESSION_ID`, `ORCHID_CONFIG` or `ORCHID_HOOK_DEPTH`, so a DIE started from inside an orchid tool doesn't make its sessions children of that one. Emacs and DIE can be open on the same sessions at once: control goes through orchid, and its files are read without a lock, as orchid's own readers read them.

**The session browser**, `\o` or `M-x orchid`, shows `*orchid-sessions*` in this window, never a split, laid out as seek laid it out in Emacs: the title centred in `─`, the search line, the columns `LABEL`, `STATUS` and `UPDATED`, and a row per session, the one changed last first. It's 78 columns wide, or the window's width if that's less, and a row wider than the window wraps at a word, as your Emacs's `global-visual-line-mode` wrapped it there. LABEL is the session's label, or else its agent and workspace (`default-die`), or else its id. STATUS is `ACTIVE` while a chat is open on it and `IDLE` otherwise, with `•RUN` while it runs, wherever the turn was started, and `DEL` or `KILL` when it's marked. UPDATED says how long ago it last changed. The selected row is highlighted, and no cursor is drawn. A window shows as many rows as fit under the six lines above them, 20 at most, and `No results` when there are none.

It reads each session's `metadata.json` rather than running `orchid list`, so it opens at once, with times and order Emacs's never had. A status that changes redraws it, and while a window shows it, it reads the sessions again every 2 s, so a turn you started from Emacs shows too. When the list changes under it, the selection stays on its session. It's read-only, and `:rebuild` brings it back with its query, selection and marks. In normal state, as your Evil has its keys:

- `j` and `k` move down and up, `p` up too (in Emacs, Evil's `p` pasted there), and `J` and `K` a page.
- `RET` opens the selected session's chat in this window, or goes to the one open on it, and kills the browser. `n` asks `Agent: ` among the valid agents and starts a chat on a new session in the browser's directory, the one of the buffer you opened it from; the browser stays. `q` kills it.
- `r` and `g` read the sessions again.
- `D` marks the session to delete (orchid archives it) and `S` to stop its turn, which only a running one has; each moves down. `u` takes the mark off. `x` asks `Execute N marked operation(s)? (yes or no)`, which wants `yes` or `no` typed out, in any case but with nothing around it, as `yes-or-no-p` does, so a bare `RET` asks again. Then it deletes and stops each in turn, in the order you marked them, keeps the marks that failed (`*Orchid Log*` says why), reads the sessions again and says what it did: `Deleted 1 session, Killed 1 process, 1 failed`.
- `/` and `a` search: what you type filters the rows, its characters in that order, in any case, in the label, the status (`run` finds the running ones) or the time it changed. Every printable key goes into the query, `j` and `q` too. `DEL` takes one back, `RET` and `Esc` stop with the query kept, and `C-g` clears it. `d` clears it from normal state too, and goes back to the first row.

**A chat**, `*orchid-chat-<agent>-<wsdir>-<id5>*`, opens in this window from the browser's `RET` or `M-x orchid-open-session`, laid out as your Emacs's: `Workspace:` and `Agent:`, a separator labelled with the workspace, the session's last 250 events, oldest first, each a collapsed 80-column stub with its tokens and local time (`[user]`, `[agnt]`, `[bash]`, `[read]`, `[edit]`, `[rslt]`, and `[fail]` and `[term]`, which Emacs showed as raw JSON), a separator before each of your messages, then `[session restored]` with the session's cumulative input, and your input under the last separator. It starts in normal state at the end, in the directory you opened it from (the browser's, for its `RET`), as Emacs's did, so `find-file` and `orchid-new-session` start there; `/new` goes by the session's. From there it follows the session, every 0.5 s while it runs and every 2 s otherwise, putting each new event in above the line that says how the turn is going. Its keys:

| Key | State | What it does |
|---|---|---|
| `RET` | insert | In your input, send it, trimmed, as `orchid send --id ID -- MSG`; an empty input sends nothing. Above the input, a newline. In normal state `RET` is Evil's, as in your Emacs. |
| `S-RET` | normal, insert | A newline. |
| `TAB` | normal, insert | On a stub or its detail, expand or collapse it; a reply's or a tool call's detail is made the first time, and a result's files are sections of their own inside it. In your input, a tab, which in insert state is part of what `.` puts in again. Anywhere else it says what it's for. |
| `/` | insert | Alone at the start of an input line, the slash menu, `/ `, which wants one of `config` (the find-file prompt at orchid's root), `exit  (quit)` (kill the chat), `kill` (`orchid stop`), `logs` and `metadata` (the session's files), or `new  (clear)` (a new session with this one's agent and directory). Anywhere else, a `/`. |
| `C-c C-l`, `S-Tab` | normal, insert, visual | The session browser, in this window. |
| `C-c C-q` | normal, insert, visual | Kill the chat. The session goes on. |

- **Sending** puts your message's stub and a separator above the input, and under the stub `[Processing: Ns]`, with the cumulative input at column 80, drawn again each second. The turn's events go in above it, collapsed, and it reads `[Finished: Ns]` once the session stops, however it stops (idle, failed, cancelled or terminated). A send that fails says `[SYSTEM] Send failed:` and orchid's reason, framed, above your input.
- **What you type stays put.** Events go in above the input as edits undo never sees, so neither your text nor your cursor moves, in insert state too, and `u` takes back only your typing. A visual selection stays on what it selected, both ends and its shape, and so does one on the ticking indicator. A window reading the transcript is taken to the end when a turn finishes, as Emacs took every window there, a selection there stretching to the end; one in your input stays.
- **Your input** starts at the blank line under the last separator, so `G`, `j` or a click there type into it too (die-vim's motions never go to the empty line after the last newline, where Emacs's input line was). What you type there comes back as it was after `:rebuild`.
- A session already running when you open it shows its indicator, counting from your last message, with its events going in above it. A turn started elsewhere, from Emacs say, shows its message and indicator as one of yours does.
- **Read-only**, as in Emacs: the `[session restored]` line and the separator under it, and the separator under a running session's indicator. The rest of the transcript is yours to edit.
- **Search** (`/ ? n N`) opens a collapsed section it lands in, and `j` and `k` step over hidden text.
- **A new session** (the browser's `n`, `M-x orchid-new-session`, or `/new`) opens `*orchid-chat-<agent>-<wsdir>-new*` at once. Type in it while orchid makes the session, and the session's chat takes its place in the same window with what you typed, still in insert state, labelled `<agent>-<wsdir>` as Emacs labelled it. A create that fails says why there.
- An archived or deleted session's chat says so once, stops following it, and sends nothing more: orchid would refuse it, and its lock would make the session's directory again. A directory left holding only orchid's lock is a session gone too.
- **After `:rebuild`** each chat comes back as a chat, in the windows it was in, rebuilt from `events.jsonl` with what came while DIE was down: the sections you'd expanded expanded again, each window's cursor and scroll on the same text, what you'd typed and your cursor's place in it. It follows again, a chat no window shows too, and if its turn still runs, its indicator ticks again, counting from your last message. One still being made makes its session, or takes the one orchid made while DIE restarted, so there's never a second; one whose session has gone says so and keeps your input. History you'd loaded with `orchid-chat-load-more-history` comes back as the last 250 events.
- `M-x orchid-chat-load-more-history` puts the 250 events before the oldest shown above them, in order; it's unbound, as in Emacs. `M-x orchid-collapsible-report-stats` says how many lazy details were made, and how long that took, in `*orchid-collapsible-stats*`.

What else there is:

- `M-x orchid-check-cli` says whether orchid is on the PATH and its version, and warns below 0.2, which this client is written for.
- `M-x orchid-list-sessions` lists each session as `  label (id)`, oldest first, in `*orchid-list-sessions*`, below, with the focus staying, as Emacs's echo area showed them.
- `M-x orchid-open-session` asks `Session ID or label: ` (or takes it after the name, `:orchid-open-session ID`), finds it by its label too, which Emacs's didn't, and says `Opened session: …`, or `Failed to open session: Session '…' not found`, as Emacs's did.
- `M-x orchid-session-browser-show` is `orchid`'s other name, as in Emacs, and `M-x orchid-collapsible-toggle-at-point` is `TAB` on a section, doing nothing elsewhere.
- `M-x orchid-new-session` asks `Agent: ` among the agents `orchid agent` says are valid, and starts in the buffer's directory. A prompt you open while orchid answers stays yours, and `Agent: ` comes when it closes, as Emacs's never took one from you.
- `M-x orchid-log-show` asks `Session ID: ` (or takes it after the name) and shows ` *orchid-log:<id>*`, beside, as `display-buffer` does: the session's `events.jsonl` as its chat has read it, the last 5 MB at first, then each line as the chat reads it, as Emacs's monitor kept it. It goes with the chat. With no chat following the session, it's Emacs's `Not monitoring session <id>`.
- `*Orchid Log*`, the client's own log, keeps its last 2,000 lines and isn't kept over a restart. You go to it as to any buffer, as in Emacs.
- An orchid command that hasn't answered in 5 minutes is stopped, with whatever it started that's still in its process group; orchid's own turn worker is in a group of its own, so it goes on.
- Nothing of orchid's runs or is read until you ask. While no orchid buffer is open, the client sets no timer. While one is, a single timer looks at the sessions for all of them: every 0.5 s while a turn runs or a send is out, every 2 s otherwise, to see a turn started elsewhere. A turn's indicator ticks each second only while the turn runs. That 2 s look is all an idle DIE does for orchid: it doesn't keep DIE's own looks at your files and its session awake, which rest at one every 5 s after 30 s of nothing from you.

## whiteboard

`\w`, or `M-x whiteboard`, is a whiteboard in a DIE buffer: die-whiteboard, an extension DIE builds beside itself, outside the product (scope D14), which your config registers. A pen first, one-key shape and arrow tools worked with the pointer, labels and a selection; a scratch board until you save it, and then a file that's SVG any browser opens; PNG export, and the PNG on the pasteboard. It draws in pixels (M3a): ink anti-aliased at the display's resolution, with round caps and joins, under the editor's own text for labels; a host that shows no pixels (Linux, until its ring) gets cells instead.

**Opening.** From a buffer that isn't a board, `\w` goes to the board used last, or with none open makes a scratch board; from a board it makes another, so `\w` twice is a fresh one. `M-x whiteboard-new` always makes one. No prompt and no file: a scratch board is `*whiteboard: scratch*` (then `*whiteboard: scratch 2*`, the lowest number free), in the directory of the buffer you typed `\w` in, and nothing asks where it goes until you save or export it, which a throwaway board never needs. `M-x whiteboard-find` asks `Board: ` for a file to open or start: the prompt descends directories as `\f` does, starting in the buffer's directory, lists `.svg` files (the one you answered last first) and directories, and `<M-CR>` takes a new name; a name without an extension gets `.svg`. `:whiteboard FILE` and `M-x whiteboard FILE` open directly, relative to the buffer's directory. A file a board has open already goes to that board, by any path to it: through a link, or in another case where the disk ignores case, as macOS's does. A missing or empty file is a new board; an SVG that isn't a whiteboard's is refused, `not a whiteboard file; open it in a browser`. A file's buffer is `*whiteboard: NAME.svg*`, its directory the file's. Either is in this window, a file's width (80 columns centred in your config) with `\z` widening it as it widens a terminal. Two windows on one board show the same view.

**The status line** says `arch.svg  pen·2  medium  12 elements`: the board's file, the tool and ink, the width, the count, ` *` while unsaved, and why a save or export failed, until the next succeeds. A scratch board's says `scratch  pen·2  medium  12 elements`, never with ` *`, since no file is behind it. `<N>` and `<I>` at the right as a terminal has them.

**Normal state** is the tool state, and the pen is its default tool. The keys, all in the board's own keymap, so `\hk` describes them:

| Key | What it does |
|---|---|
| `p` | The pen, which draws freehand with the current ink and width. |
| `r` `c` `a` `t` | One shot: the next drag draws a rectangle, an ellipse or an arrow, the next click places a label; then the pen again. |
| `l` | With nothing selected, one shot: the next drag draws a line. With a selection, nudge it a cell right. |
| `h` | With nothing selected, the highlighter on or off (the pen at 16 px and 35 %). With a selection, nudge it a cell left. |
| `e` | The eraser on or off: a drag erases every element it crosses. |
| `v` | Select: a click selects the element under the pointer, a drag a marquee (what it holds whole), a drag on the selection moves it. `j` `k` nudge a cell down and up (`h` `l` too), `x` and `Del` delete, `y` duplicates a cell down and right and selects the copies. |
| `Space`, held | The tool dial: the eight tools around the pointer on a ring two and a half cells out, their names outside it, pen north then clockwise rect, ellipse, arrow, line, text, eraser, select. Move past the dead zone (a cell around the centre) in a tool's direction and let go, and the tool is armed as its key would arm it: one shot for the shapes and text, the eraser on or off, the pen and select for good. The hovered name is a chip, and a readout under the dial says what letting go does (`pen: ink 2 · medium`, `rect: once`, `eraser: on`, `select`); with nothing hovered it says what's armed, dimmed. For a tool that draws with ink (not the eraser or select), go on half a cell past the ring, on a move after the one that hovered the tool, and its ink arc opens, five cells beyond the ring, with the tool's chip past it: the six inks clockwise in their own colours, placed so the ink you have is in the tool's direction, so straight out keeps it. The arc's first band, a cell and a quarter deep, picks nothing, so a flick that overshoots the ring changes nothing. Past its guide, marked `2`, the angle picks the ink (past either end, that end's), and for all but text the distance picks the width, thin, medium, then thick, a cell and a quarter each, at the guides marked `2` `4` `8`; the needle turns solid, its dot shows the ink at that width, and the readout says it (`pen: ink 3 · thick`, `text: ink 5`). The names the arc and its guides cross give way and the rest dim. Letting go there arms the tool and sets the ink and width as `1`..`6` and `[` `]` would, the selection's too, as one undo step (none if it has them already); back inside the ring is the tools again. Letting go before the arc opens, in its first band, or where the move that hovered the tool landed never changes the ink or width. Let go inside the dead zone and nothing changes; a click while it's open picks too, at whichever stage, and leaves no dot; `Esc`, any other key, a resize or the focus going closes it (not `C-w w` between two windows on the board: the board keeps the focus, and the dial). Shift pressed while Space is held changes nothing. It opens under the pointer, where the board is now, after the wheel or `+` moved the board under it. The right button held is the same dial (The pointer, below). It's the board's own key, so `\hk` then Space says it goes to the whiteboard surface, which handles it (the key prints as a blank there, as a macro register writes a Space). |
| `Esc` | Drop the selection and take back whatever the pointer was doing, back to the pen. |
| `1`..`6` | The ink, for what's drawn next and for the selection: the default foreground, then the theme's red, yellow, green, blue and magenta (faces `whiteboard-ink-1`..`6`, which a theme restyles). |
| `[` `]` | The width, thin, medium or thick (2, 4, 8 px), for what's drawn next and for the selection. |
| `u` `C-r` | Undo and redo, one gesture, command or label at a time; `Cmd-Z` and `Cmd-Shift-Z` too, while a label is typed as well. |
| `+` `-` `0` | Zoom in and out about the area's centre, a quarter at a time between 0.25 and 4, and back to 1:1 with no pan; Cmd with the wheel zooms about the pointer. A board drawn in cells is at 1:1, and `+` and `-` say so. |
| `E` `C` `S` | Export (asks `Export to: `), copy the board to the pasteboard as a PNG, save now (a scratch board asks `Save board as: `). |
| `:`, `C-w …`, `\z` | die-vim's command line and window keys, and the width toggle, bound here since a board has no text for die-vim's keys to come through. Your leader's other keys work as anywhere. |
| `ZZ` `ZQ` `C-^` `C-o` | Evil's reflexes, bound here for the same reason: write the board and close its window (as `:x`; a scratch board asks where first, as `S` does), close it, flip to the buffer used before, back along the jump list. `:w`, `:wq` and `:x` still say the buffer has no text: a board writes itself (`S`, autosave). |

**The pointer.** A left drag draws with the tool, and the stroke shows as it goes. The right button held is the tool dial, so drawing and switching tools need no key: it opens where the button goes down, the drag hovers the tool in its direction, and letting go arms it, or in the dead zone changes nothing, so a right click is harmless (the eraser is `e`, or west on the dial); dragging on past the ring opens the ink arc, as with Space, so one right drag picks a tool, an ink and a width, and a quick one that overshoots picks the tool alone; a right click mid-stroke opens nothing and ends nothing, the stroke going on to where the left button lifts. Shift while dragging a rectangle or ellipse makes a square or circle, and holds a line or arrow to an axis. A line or arrow drawn against a rectangle or ellipse, within 12 px of it, binds to it and lands on its outline, and follows when the shape moves. The press that gives the window the focus only focuses it and draws nothing, so clicking into a board leaves no dot, from another of DIE's windows or from another app (macOS activates DIE first and delivers the click right after; a press within 150 ms of the focus coming on its own is that click). A click that ends a label does nothing else either. The wheel pans. A gesture cut short keeps what it did: a tool key, `u` or the focus going (Cmd-Tab) mid-move or mid-erase ends it where it stands, logged, so `u` takes it back; `Esc` mid-gesture takes it back itself, the move returned and the erased put back. A stroke leaving the window stops at its edge. A double click on a label, with `t` or in select, edits it.

**Labels** are typed in insert state: `t` then a click places one, `S-RET` starts a new line, `BS` takes a character back, `Esc` or `RET` ends it, every time, keeping it if it has text and dropping it if it hasn't, with the pen back. On screen they're cells in the editor's font, over the ink, so they don't grow with the zoom (their corner follows it); a PNG export draws them with DIE's own IoskeleyMonoTerm.

**Files.** A board's file is written a second after the last change (one timer, only while something's unsaved), when its buffer is killed, and when DIE restarts or quits; `S` writes now. There's no `:w` to remember and `:q` never refuses. The write goes to a temporary file renamed over the old one. A write that fails shows in the status line and the messages, and a restart (`:rebuild`) that can't write a board keeps the board itself in the session, so it comes back as it was, unsaved still, with a message, and is written once it can be. A scratch board is never written by itself: no autosave, nothing when its buffer is killed (that discards it, as killing Emacs's `*scratch*` does), and a restart or quit keeps it in the session, not on disk. `S` on one asks `Save board as: `, the `Board: ` prompt's way from the board's directory, but `<CR>` takes the name as you typed it, as Emacs's `write-file` does: a board it lists is chosen only once you move to it with `<Down>`, and `<Tab>` completes a name or a directory. A name not ending in `.svg` gets it (`diagram.png` is `diagram.png.svg`), a file there already asks `File NAME exists; overwrite? (y or n)`, and another open board's file is refused, by any path to it. Once written it's that file's board, as if `Board: ` had opened it: `*whiteboard: NAME.svg*`, in the file's directory, written a second after each change. `ZZ` asks the same and then closes the window. The file is plain SVG 1.1 in the whiteboard's own dialect: `<path>`s with round caps and joins, `<rect>`, `<ellipse>`, `<line>` with a `<marker>` arrowhead, `<text>` in a monospace family, a `<style>` naming the inks, and `data-wb-*` attributes (the version, each element's id, ink and width, a shape's corners as given, a label's text as typed, a line's bindings) so a board reads back exactly. `M-x whiteboard-open` saves it and opens it in your browser (`open`, or `xdg-open` on Linux); a scratch board's goes to a temporary file, which is what the browser opens.

**Export.** `E` asks `Export to: `, filled in with where this board exported last, or else `NAME.png` beside its file, or `board.png` in a scratch board's directory (`board-2.png` if that's taken); the prompt descends as `Save board as: ` does and lists directories and PNG and SVG files, so `E RET` writes the path it shows. The answer's extension says what's written: `.png` a PNG rasterized from the model rather than the screen, at the option `png_scale` (2, so a 400 px board is 800 px) on `export_background` (`theme`, the default, `white` or `transparent`); `.svg` the picture without the dialect's attributes; anything else is refused, and so is an open board's own file, by any path to it. A file there already asks to overwrite, unless it's the one this board exported to last and nothing else has written it since. `M-x whiteboard-export png` or `svg` writes `NAME.png` or `NAME.export.svg` beside a board's file without asking, unless that's an open board's own file; on a scratch board it asks, filled in with that extension (`board.png`, `board.export.svg`). `C` puts the PNG on the pasteboard, through `osascript` on macOS and `wl-copy` or `xclip` on Linux, whichever is on the PATH. Each runs in a job and says what it wrote.

**On screen.** The board is one pixel buffer the size of the window's area, drawn by tiny-skia on the main thread and placed under the glyphs, so the theme's background and the labels' cells show through and over it: strokes with round caps and joins at 2, 4 or 8 logical pixels, the highlighter at 16 and 35 %, shapes and arrowheads filled and anti-aliased, the selection a dashed outline 3 px outside each element, the marquee a dashed box. A pointer sample draws only the pen's new segment and presents that rectangle; a shape or the highlighter is drawn again whole as it grows; the tool dial is drawn over the picture the same way, as line art after the reel its design comes from: no panel, but a scrim of the theme's background held under its names and fading out a cell past them, so it reads over ink; the tool ring dotted in the dial's grey with a tick between sectors, the hovered sector's stretch thick in the accent, the dead zone a fainter dotted circle, a reticle at the centre, a dotted needle to the pointer ending in the accent's dot, and a faint crosshair through the pointer, within the dial's own square; stage two's ink arc in the inks' own colours with a tick between them and a T at each end, the picked one thick, its guides faint with their `2` `4` `8` past the arc's end, clear of the lines and of each other, and once a band picks, the needle solid with a tick at each guide it crosses and its dot the ink at the width, on a faint disc of it where that's narrower than the dot. The names and the readout are cells over it, the hovered name a chip, the accent behind the background, past the arc in stage two, so between the ring and the arc there's only the needle and the guides (faces `whiteboard-dial` and `whiteboard-dial-accent`: mono-dark's mid grey and red, else `shadow`'s grey and the theme's ANSI red; a label under the dial dims with the ink, the whole label). What stays while the pointer moves is kept, so a move draws only the needle, its dot and the crosshair again, about 0.1 ms over 1,000 strokes, and a change of what's hovered draws the rest again, about 0.5 ms (1 to 1.8 ms at your 16 pt cells, whose dial is twice the size); a change to the board draws its region again (a wide one, as a selection of most of the board being dragged, in bands across the cores like a whole redraw); undo, zoom, a resize, a theme change or the selection draw it all; the wheel moves the picture by whole pixels and draws the strips it uncovers. The buffer grows with the area and never shrinks, so a second window of another size on the board, or `\z` back, shows its top-left part rather than re-making it. On a board of 1,000 strokes a sample costs about 0.1 ms and a full redraw, drawn in bands across the cores, about 25 ms in a release build (the numbers are in docs/m0-log.md, calls 1025 and 1043). **In cells** (a host without pixels, or the option `pixels: false`) rectangles, lines and arrows snap to cells and draw in the box glyphs DIE joins across cells, with `▶ ◀ ▲ ▼` for arrowheads; ellipses and strokes are braille, two by four dots a cell in the ink's colour, the newest element winning a cell; the highlighter is faint; the selection is reverse video; labels are text; the tool dial is its eight names around a `+`, the hovered one a chip, and the readout under them, what's under the dial dimmed; past the ring the six inks are swatches, `██` in each ink along the arc, the chip past them, the picked one between brackets, and the width is only in the readout; the other names dim, and give way only to a swatch.

**After `:rebuild`** each board comes back with its view, tool, ink, width, selection and last export: a board's file from the file, which was written at the hand-over, and a scratch board from the session, with its name and directory (an empty one isn't kept); the one used last in this window, the rest open in the background. Unsaved changes to a file at a crash are at most a second old; a scratch board's, as old as the session's last write, a second or so after you stopped (at most five while you keep going).

**Options**, as your config sets them (it sets none): `font_dir` (where the fonts are, for the exporter; DIE's own rule by default), `png_scale` (2), `export_background` (`theme`), `full_width` (a new board the window's whole width rather than a file's), `autosave` (a second), `pixels` (true; false draws every board in cells). Nothing of the whiteboard's runs until you open a board, and nothing while every board is saved.

## jellyfish

`M-x jellyfish`, or `:jellyfish`, is your ASCII jellyfish swimming in a DIE buffer, `*jellyfish*`: die-jellyfish, an extension DIE builds beside itself, outside the product (scope D14), which your config registers. It's your program's animal and its effects, worked out from the clock alone and drawn on your theme's background: the bell and its lip, the arms, the tentacles, the coats and the flash between them, the swirl it forms from, the halos, the sparks, and the glint where it's about to be. The source listing, the readouts and the command line are gone. The five rows the readouts kept clear are two, one above and one below, with the animal centred between them.

**When it shows.** DIE started with no file opens on it, where the empty `*scratch*` was: from the Dock, Finder or `open`, or a bare `die` that finds no DIE running. Over a session that brought back one window it takes that window, with every buffer back behind it, and `q` uncovers the one that was there. It stays away from a session's splits, from a start with a file named (`die foo.rs` opens on the file, and no jellyfish is made), from `:rebuild` and `:restart`, which bring back what was on screen, and from `die --check`. A restart that brings nothing back gets it where `*scratch*` would have been. A file that arrives after the launch takes its window, with the jellyfish still there behind it: a Finder double-click or `open -a DIE file` that starts DIE, and `die --wait` with no DIE running, which starts one and then sends its file, so those show a frame of jellyfish first. `:jellyfish` shows it in this window at any time: the one already swimming, or a new one from its first spark.

**Keys**, in normal state, the only state it has. The first three rows are in the jellyfish's own keymap, so `\hk` describes them:

| Key | What it does |
|---|---|
| `q` | Let it go (`jellyfish-close`): the buffer is killed, and the window the launch or `:jellyfish` put it in shows the buffer it covered there, whatever was made behind it meanwhile. If that window has left it and come back by another way (`C-^`, `\]`), or `q` is pressed in another window on it, each window that showed it shows the buffer you used last, as when any buffer is killed, or an empty `*scratch*`. |
| `:`, `C-w …` | die-vim's command line and window keys, bound here as on a [board](#whiteboard), since a jellyfish has no text for die-vim's keys to come through. |
| `ZZ` `ZQ` `C-^` `C-o` | Evil's reflexes, bound here for the same reason: close its window (both, as `:q`, since there's nothing to write, so in the last window they quit DIE), and flip to the buffer used before, the jellyfish staying behind it (both: `C-o` is `C-^` here, since die-vim's jump list starts from a text cursor, which a jellyfish hasn't, and that buffer is where the first `C-o` from here would go). With nothing behind it they say `No other buffer`. |
| `Esc`, `Ctrl-[` | Nothing, as in normal state anywhere; after `C-w` or `Z` it drops the key begun, and says nothing. |
| Any other key | `i is undefined`, as on any buffer that isn't text. Typing doesn't lift it. |

Your leader's keys and DIE's own work as anywhere, so `\f`, `\p`, `\]`, `\e` or `:e file` put what you asked for in its window, with the jellyfish a buffer behind it (`\]`, `C-^`). It takes no leader key.

**When it swims.** While a window shows it and you've touched DIE in the last five minutes. With no window on it, it stops, and shown again it goes on from where it stopped: the opening plays once for a buffer, and again only after `q` and `:jellyfish`. After five minutes without a key (`rest_after`) it rests, a still picture, and the next key's command wakes it where it stopped; so do a click anywhere in DIE, a key or the pointer on it, and DIE's window taking the keyboard while the jellyfish's split has the focus (with the focus in another split, coming back to DIE leaves it still until your first key's command). Typing into a terminal in another split doesn't wake one at rest, as those keys run no command. It swims whether or not DIE has the keyboard, since DIE's window opens without it. A pause never jumps it ahead: each frame adds the time since the last one, a quarter second at most, as your `clock += dt.min(0.25)` did, and a new one's first frame a thirtieth at most, so the opening starts at its start however long DIE's window took to open.

**On screen.** Every cell's background is the theme's, and the colours fade into it where yours faded to black, so a halo or a spark's tail ends at the paper rather than as a dark speck on it. On a dark background nothing else about the inks changes. On a light one, white would be the paper, so the brightest ink is the theme's foreground and the pigments are deepened (to 0.62 of themselves, toward black): that's measured for contrast and not yet seen, since mono-dark is the only theme. A theme set while it swims re-tones it at the next frame. It's the window's whole width (`full_width`), so the water's glitter and the sparks don't stop at an invisible wall, and `\z` narrows it to a file's width and widens it again. The animal grows with the window between about 49 columns by 30 rows and 132 by 77 (for cells twice as tall as wide), and in a smaller window it's cut at the edges rather than drawn smaller, as in a small terminal. The status line shows the directory, as on any buffer, and no cursor is drawn.

**Not kept.** It isn't in the session: a restart doesn't bring it back, and a window that showed it shows the buffer you used last, which is the one it covered unless you've shown or made another since, your cursor where it was, though that window's jump list is gone, as after a restart with a terminal in it. Nothing of it is written anywhere.

**Options**, as your config sets them (it sets none): `water` (true: the dust and the four-point twinkles in the water around it), `shoal` (false: the far-off little jellyfish), `full_width` (true, where a board's is false), `rest_after` (five minutes; `None` never rests). **What it costs:** nothing until it's shown. While it swims, one timer at 30 a second, a covered or minimized DIE's too, until the five minutes are up. At rest or with no window on it, nothing: no timer runs.

## markdown

`\m` in a markdown file shows it as a page, drawn as GitHub draws a README, and `\m` on the page shows the file again: die-markdown, an extension DIE builds beside itself, outside the product (scope D14), which your config registers. A file opens raw, as it always has. The page is a buffer of its own, `NAME *page*`, shown in the file's window and drawn in pixels across the window's whole width. It uses the system's proportional font (San Francisco on a Mac, at the sizes, weights, kerning and spacing GitHub's stylesheet asks of it), in a centred column at most 980 CSS px wide, in your theme's colours. The file is never touched: the page reads it and follows it, and raw is where you edit.

**Where.** A buffer visiting a file named `.md`, `.markdown`, `.mkd`, `.mdown`, `.mkdn` or `.mdwn` has the `markdown` mode. `\m` is a key of that mode's keymap and of the page's, so it's a key only there: in any other buffer `\m is undefined`. `:markdown-toggle`, or `M-x markdown-toggle`, does the same on any text buffer, a `*scratch*` with markdown in it too.

**Where there's no page.** Where the host shows no pixels (Linux, until the wgpu ring), where the system has no font the page knows, or with `page` off, `\m` gives the view in place instead (below).

**What the page shows.** GitHub-flavoured markdown at GitHub's geometry: 16 px text on 24 px lines, 16 px between blocks, 45 px of padding (15 in a window under 768 CSS px).
- Headings: 32, 24, 20, 16, 14 and 13.6 px semibold; h1 and h2 over a hairline, h6 muted.
- Inline text: emphasis, strong, struck text, inline code as a pill, links underlined in the link face's colour, footnote references as raised numbers with the notes gathered at the foot and a way back to each reference.
- Lists: bullets as disc, ring and square by depth, numbers right-aligned, tight and loose lists, and task boxes drawn (checked in the theme's green).
- Quotes and alerts: quotes with a 4 px bar and muted text; GitHub's five alerts (`> [!NOTE]` and its kin) with a coloured bar, icon and title.
- Code blocks: rounded panels, coloured by language (below), long lines wrapped with a mark.
- Tables: sized to their content, with a 1 px grid, a semibold header, every second row shaded, and cells that wrap. A table too wide for the column runs into the right margin, and then gives up its cells' padding, before any word is cut.
- Rules and pictures: a rule is a 4 px bar. Pictures are PNG, scaled to the column; a path from `/` is from the repository's top, as on GitHub. A missing or remote picture, or another format, shows its alternative text behind a small picture mark, and `<CR>` on it opens it.
- HTML: `<br>`, `<kbd>`, `<sub>`, `<sup>`, `<b>`, `<i>`, `<code>`, `<a href>`, `<a id>` and `<a name>` as anchors, `<img>`, `align="center"`, and `<details>`, closed unless it says `open`. `<CR>` or a click on a summary opens and closes it, and it stays as you left it while the file has it. Comments and other tags vanish, their text kept.
- Front matter is left out; with `front_matter` on it's a table of its keys.

**Code colours.** A fenced block is in its language's colours, by the fence's first word: Rust, shell and console sessions, TOML, INI, JSON, YAML, Python, JavaScript and TypeScript, C and C++, Go, Java, Kotlin, Swift, Ruby, Lua, Emacs Lisp and the other Lisps, SQL, HTML and XML, CSS, diffs, Markdown, Dockerfiles, makefiles, Nix, Zig and Haskell. A block with no language, or one it doesn't know, is plain, as GitHub draws it. In mono-dark the colours are the greys of highlight.js's grayscale-dark, which your preview colours code with; in the GitHub palettes they're GitHub's.

**Keys on a page.** A page is for reading: it has no cursor, and these keys are its own (`markdown-page-*`). A key it hasn't got is undefined there, `/` and `y` among them.

| Key | What it does |
|---|---|
| `\m` | The file again, in this window (`markdown-toggle`). If you scrolled, the cursor goes to the line at the page's top; if you didn't, it's where you left it, and `\m` from there comes back to the same pixel. |
| `j` `k`, `<Down>` `<Up>`, `<C-e>` `<C-y>` | Scroll a step, 60 CSS px, two lines and a half of text. A count repeats, as for the rest. |
| `<C-d>` `<C-u>` | Half a window. |
| `<C-f>` `<Space>` `<PageDown>`, `<C-b>` `<S-Space>` `<PageUp>` | A window less an eighth. |
| `gg` `<Home>`, `G` `<End>` | The top, the bottom. |
| `]]` `[[` | The next heading, the one before. |
| The wheel, the trackpad | By pixels. |
| `<Tab>` `<S-Tab>` | Ring the next link, or the one before, starting from what's in view, and scroll to it. The status line says where it leads. `<Esc>` takes the ring off. |
| `<CR>`, a click | Follow the ringed link, or the one clicked (`markdown-follow-link`). |
| `<C-o>` `H`, `L` | Back to where a link was followed from in this window, and forward again, across pages. `<C-i>` is `<Tab>` to DIE, so forward is `L`. |
| `:`, `<C-w>…`, `ZZ` `ZQ`, `<C-^>`, `\z` | As everywhere. `\z` narrows the area the page is centred in. |

**Links.** `#heading` scrolls to the heading, by GitHub's rule for anchors and in any case. `#fn-1` and the like go to a footnote, `#name` goes to an `<a id>` or `<a name>`, and a place inside a closed `<details>` opens it. A markdown file opens as its page in this window, at the heading or the line the link names (`notes.md#set-up`, `notes.md:12`). Another file opens as text, as `:e` would; `<C-o>` or `<C-^>` there goes back to the markdown file at the line the page showed, where `\m` brings the page back as it was. A path from `/` is from the repository's top (the nearest directory with a `.git`). A web or mail address, a picture, a PDF or an HTML file goes to `open`, so a web page is your browser's.

**Two windows.** A page in two windows is a view in each, as two browser windows on one page are: each is laid out for its own width, with its own place, its own ringed link and its own way back. A window that leaves a page another window still shows comes back to it where it was.

**What it follows.** A page is laid out again when the file's text changes (an edit in another window, `:e!`, the file changing on disk), when its window's width or the display's scale changes, when the theme's colours change, and when a picture it was waiting for arrives. It keeps your place through all of these. A page no window shows is put away when the command ends: its file remembers where you were, and its next page starts there. **Kept:** the page the focused window showed comes back after `:rebuild` and a restart, in that window and at the same place; a file whose page you'd left remembers where you were.

**Options**, as your config sets them (it sets none):
- `extensions`: the six above.
- `front_matter`: false leaves it out; true shows it, as a table on a page and dimmed in place.
- `opener`: none means `xdg-open` where there is one, else `open`.
- `page`: true.
- `palette`: `Theme` (the default), your `markdown-*` faces; or `GithubDark` and `GithubLight`, GitHub's own colours.
- `fonts`: none means DIE's own fonts are found as DIE finds them; they're the last resort on a system with no sans the page knows, and fill in symbols the sans lacks.

**Faces.** A page reads its colours from the faces the view in place draws in:
- text and background from `default`;
- headings from `markdown-h1` to `-h6`;
- links from `markdown-link`, underlined if the face is;
- inline code and code blocks from `markdown-code` and `-code-block`;
- quotes and footnotes from `markdown-quote`;
- the grid, bars and rules from `markdown-rule`;
- code colours from `markdown-code-keyword`, `-string`, `-comment`, `-number`, `-function`, `-type`, `-constant`, `-meta`, `-variable`, `-tag`, `-attr`, `-inserted`, `-deleted` and `-heading`;
- the alerts from the theme's ANSI colours.

mono-dark styles them from your preview's stylesheet (`mono-dark.css`) and its code theme (`grayscale-dark`). A theme that styles none of the code faces draws code plain.

**What it costs.** Nothing for a file that's raw. On this Mac, in a Retina window: `\m` shows this guide (80 KB) in about 18 ms and the M0 log (480 KB) in about 29; a scroll step takes about 2 ms, and following an edit about 4 ms here and 13 ms there, twice that with the page in two windows of different widths.

### The view in place

Where there's no page, `\m` shows the file rendered in its own buffer: the markup hidden under decorations and never removed, the text styled in the cell grid's one size of letter, so headings differ by weight, underline and brightness. A code block is a filled box, a table is aligned with `│` between its columns, `•` `◦` `▪` and `☐` `☑` stand for bullets and task boxes, a quote has a `▎` bar, a picture is `‹image: alt›`, and HTML and footnote labels show dimmed as written. Everything else is as written: nothing is reflowed. die-vim's keys that move, search, select and yank work on what's shown, and the buffer is read-only while rendered, since a key at the edge of hidden markup would change what you can't see: `\m` again to edit. `<CR>` on a link follows it as on a page. It's planned again when the text or its width changes, and the session keeps which buffers have it.

## fig

`\v`, or `M-x fig-toggle`, shows the buffer's data as a chart, a network graph or a gantt, and `\v` on the figure shows the buffer again: die-fig, an extension DIE builds beside itself, outside the product (scope D14), which your config registers. CSV, TSV, JSON rows, JSONL, fig's own files and die-fig's specs all draw; bare data gets a guessed chart (a time or ordered number column across and a line for each number column, categories as bars, two numbers as points, one as a histogram), a table with an `id` and a `parent` column a tree (an org chart from a CSV), and a table with a `start` column of times and an `end` or a `duration` a gantt. fig's graph JSON (`nodes` and `edges`) and a spec of `"type": "graph"` draw as graphs, a spec of `"type": "gantt"` as a gantt (below), a spec of `"type": "dashboard"` as a dashboard of panels (below), and a `stat`, `meter` or `sparkline` alone as a dashboard of that one tile. It draws in pixels, antialiased in the system's font; a host that shows no pixels (Linux, until its cells) says `fig: this host shows no pixels yet` and makes nothing.

**Opening.** `\v` on a text buffer makes `NAME *fig*` and shows it in this window, the window's whole width, in the buffer's directory; one figure a source, so `\v` again from the source goes back to it. In visual state `\v` charts the selected lines as they are, in `*fig: selection*` (die-vim's `gv` brings the selection back). `:fig FILE` charts a file, by its buffer if one visits it and otherwise from disk; `:fig !cmd` runs the command once in the buffer's directory and charts what it printed, with no question since you typed it; `:fig` alone is `\v`. `\v` on a figure goes back to the buffer it follows (or the one you came from, or its file), and a figure no window shows any more goes then, its view kept for the next `\v` (or the same `:fig`) on that source. A `.fig` or `.fig.json` file opens as its figure, its text behind it: `\v` flips to the text and back, and a `.fig` that can't draw opens on the error figure (below). Opened again (`:e`, `:b`, a jump), a `.fig` opens as you last looked at it, and its text reached from its own figure (`\v`, `⏎` to an error, `:b` its name, `C-o`) stays text. One you're writing stays text: a new, empty `.fig`, and a buffer you save under such a name. CSV, TSV, JSON and JSONL files open as text, as ever. `M-x fig-spec` writes the figure as a spec into a new, unsaved buffer `NAME.fig` beside the data, shown as text to edit (`:w` writes it there; where a file of that name is there already, the buffer has no file): a guessed chart becomes one to edit, its data by the file's path (a guessed gantt too, with its settings as `s` left them).

**The status line** says `requests.csv  3 series` (a graph's `services.json  18 nodes  25 edges`, with how many groups are hidden and nodes pinned; a gantt's `release.fig  11 tasks`, with how many have no row while their name is hidden; a dashboard's `health.fig  6 panels`, or `panel 2/6` once one has the focus), then how many are hidden, `following` while the view follows live data, and while the last build failed what the badge says (`Error · line 14`), until one succeeds. `<N>` at the right as anywhere.

**Normal state.** The cursor sits on the data the way a text cursor sits on text: none while a figure opens, and the first `h` `l` `j` `k`, click or search puts it there. It's the pinned card: its crosshair, dots and card show whenever the pointer isn't hovering the plot. The view follows it as a window follows the text cursor; other keys move the view and leave the cursor where it is. Every key is a `fig-*` command in the figure's own keymap, so `\hk` describes it and your config can rebind it.

**A graph** is drawn as the design's m3: nodes as discs coloured by their `group` (a legend for two or more), sized by a `size` field or by their degree, edges as hairlines with an arrowhead ending at the ring when they're directed, labels in the text's colours on whichever side is free, the busiest kept where they'd crowd. It's laid out once, in a job, the last frame up until it's done: fig's stress layout, a tree for a forest or a table's parents, or layers for a directed graph with no cycle, unless the spec or `s` says which. Its keys are a chart's where they mean something: `h` `j` `k` `l` go to the nearest node that way (the first puts the cursor on the node nearest the middle, the view as it is), `]` `[` go round the cursor's node's neighbours clockwise from straight up, and again round the same node, `gg` `G` to the first and last node in the file, `+` `-` `0` zoom about the cursor and fit, `zh` `zl` `zj` `zk` `zz` scroll and centre, `x` `o` `X` act on the cursor's node's group, `m` sets the reference at the cursor's node, and the view keeps the cursor in sight, recentring on it at the same zoom when it would leave. The cursor's node wears a ring, its neighbours and the edges to them stay bright and the rest dims, until `Esc` lets it go; a label always sits clearly nearer its own node than any other, and the focused node's lies on a ground that hides the dimmed nodes under it. In a tree or layers an edge between two nodes of one rank arcs off the rank, clear of the nodes between, and layers sit a parent over its children; a self-loop goes where its node has no other edge. `s` turns the labels on or off, picks the layout (`force`, `tree`, `layered`; the one drawn changes nothing, and a tree keeps the spec's root), and `relayout` lets every pin go; each is an undo step, and undoing a layout brings back the pins and the window it had. The pointer: hover finds a node and then an edge, which lifts or thickens and shows its card (a node's label, group, degree and first fields; an edge's ends and its label or weight), and a node hovered for 100 ms comes into focus, its neighbours bright and the rest dimmed, letting go after as long, so crossing between two nodes doesn't flash. A click puts the cursor on a node, or on an edge's nearer end; the background does nothing. ⇧-click sets the reference node, and with it the hovered node or the cursor's shows the shortest path, its card saying how many hops. A double click on a node or an edge opens its detail, and on the background fits. ⌥-click shows only the node's group (one with no group says so). A drag on a node moves it with the place you took it by kept under the pointer, its edges and label following, and pins it where you let go (a small dot on its ring), one undo step for the move and the pin, with nothing else moving; in a tree or layers it slides along its rank only; it stays inside the graph's part of the window, never under the panel; `Esc` mid-drag eases it back, and `u` lets it go again. A card stays by what it's about, says less (its own fields go first) rather than cover a neighbour, the title or the legend, keeps off the edge it's about, and a label it would cut goes whole. A drag on the background, ⌥-drag and a middle drag pan, 1:1; the wheel pans both ways and ⌘-wheel zooms about the pointer, a burst one undo step. Every rule of a chart's pointer below holds. Editing the source keeps the view and the pins of every node whose id survives, and the layout `auto` picked, so an edit that turns a tree cyclic doesn't lay it out anew; an edit that turns a table with parents into plain data (renaming its `parent` column) charts it fresh, the graph's window and pins let go.

**A gantt** is a plan over time: a task a row under its group's heading, its label in a gutter at the left and its bar under a time axis along the top, the part of it done solid where the plan tracks progress, a milestone a diamond with its date, a task with parts a thin bar across them, an arrow from each task to those that come after it (in the warning colour where one starts before the task it waits for ends), today's line, and the spec's marks. Bars are coloured by group, or by the spec's `color` field with a legend. The rows don't stretch: a short plan leaves the rest of the window empty, and a long one scrolls under its axis, a thin scrollbar at the right. Its keys are a chart's where they mean something: `j` `k` go to the task below or above (the first puts the cursor on the first task in view), `h` `l` to the task that starts before or after, `]` to a task that comes after the cursor's and `[` to one it comes after (`]` again goes round those that come after the same task, or on down the chain where there's only the one), `w` `b` to the next or previous milestone, `gg` `G` to the first and last task, `H` `M` `L` to the top, middle and bottom task in view; the view keeps the cursor in sight, scrolling its row in and bringing its bar into the time shown when it's wholly outside. `+` `-` zoom the time about the cursor's task (or the middle), no closer than a minute across the plot and no further out than twenty times the plan; `0` fits the plan's time again, the rows where they are; `zh` `zl` `zH` `zL` scroll the time and `zj` `zk` the rows, and `zz` centres the cursor's task. `x` `o` `X` hide, show alone and show again the name that colours the cursor's task (its group, or its `color` field's value), its tasks' rows going with it; a task no name colours says so. `/` finds a task by its label or its id; `⏎` opens its detail: its dates as the plan worked them out, its fields, then the tasks it comes after and those that come after it, each a row that names its task, so `⏎` there takes the cursor to it. `s` turns the `grid`, the `axes`, the `links` and the `today` line on or off, each an undo step, the plan built again from the data in hand with nothing read again. The pointer: hovering a task, by its bar or its label, lights its row, its arrows and the tasks at their other ends and shows its card (its start and end, or when for a milestone, its duration, progress and group, what it comes after, the spec's `tooltip` fields, and a conflict by how much), with no delay; off any bar, a hairline and the date under the pointer on the axis. A click puts the cursor on a task; a heading and the background do nothing. A double click on a task opens its detail, and on the background or the axis fits the plan. A drag across the plot is a brush, and letting go zooms the time to it, one undo step (`Esc` mid-drag drops it); ⌥-drag and a middle drag pan the time and the rows, and a drag on the axis the time alone. The wheel scrolls the rows when they overflow and it goes up or down, and otherwise pans the time; across, it always pans the time; ⌘-wheel zooms the time about the pointer; a burst keeps the meaning of its first event and is one undo step. On the legend a click hides or shows a name, and ⌥-click or a double click shows only it. Keys, a brush's release and a fit ease; the hand's moves never do. Editing the source keeps the time shown, the rows' scroll and the cursor, by its task's id: a task that's gone lets the cursor go, and a name that's gone leaves what was hidden. `?` shows a gantt's keys.

**A dashboard** is a figure of figures, laid out as the design's m4: its title, the time range chip under it (`Last 6 hours`, or a zoomed range's ends, `10:05 – 11:40`), the live status at the right while a command feeds it (`live · updated 12 s ago`, `updating…` while a run goes, `error · 2 m ago`, `paused` while you've panned away from the newest, `asking…` while a command waits for your yes, `not run` after your no), then its rows of panels, each a rounded frame with its figure's own title: a chart, a graph, a gantt, a heatmap, a stat, meter or sparkline tile, another `.fig` (a dashboard there a framed group of its own). A gantt's panel is at least its axis and four rows high and scrolls its own rows inside; its time is its own, not the dashboard's shared time. A row of tiles takes the tiles' height, its tiles' labels level and their values one size, and the other rows share the rest; when they don't fit at their least, the rows scroll under the header with a thin scrollbar at the right. It opens at once as frames and titles, each data file read in a job of its own, and each panel draws as its data comes; a panel that can't draw shows its error figure in its frame, which answers as it does alone (a click on it, or `!` on the focused panel or the one under the pointer, turns it over to its log, where `j` `k` `gg` `G` `C-d` `C-u` and the wheel move, and `⏎` or a double click on an entry goes to its place), and one whose rebuild fails keeps its figure with the badge (a click on the badge, or `!`, shows its error as a log over it). The panels on the dashboard's `time` field are linked: they share one time, so a zoom, pan, brush, scroll or key on one moves them all, eased together and one undo step for all (a dashboard has one undo history); `0` and a double click on a linked plot put the time back to its range. Hovering a linked chart shows its crosshair and card, and in every other linked chart a dashed line at that moment with each series' dot and value, and in each tile with a trend its mini crosshair, as m4 has it; with nothing hovered the focused panel's cursor does the same. `"tooltip": "shared"` gives every linked chart its card. `Tab` focuses a panel, ringed in the border grey; a click on a panel focuses it and puts its cursor there, on its title focuses only, and on a tile puts its cursor on the trend's newest point (`h` `l` move it). Every key of a panel's figure acts on the focused panel: `h` `j` `k` `l`, the `z` keys, `+` `-` `0`, `x` `o` `X`, `m`, `⏎` (its detail beside the dashboard, which lays out in what's left; a tile's, its numbers), `/` (found in that panel), `s` (that panel's settings: a chart's, a graph's labels and layout, or a gantt's grid, axes, links and today line) and `t` (its data); a key that doesn't apply says so for the panel it's on (`this panel is a stat`), and a key moves another panel's hover card away; the first such key with no panel focused focuses the first that draws. A double click on a title or a tile shows it full size, as `f` does. The wheel scrolls the page while the rows overflow and it goes up and down; across, with ⇧ or with ⌘ it's the panel's under the pointer, and when the rows fit it's always the panel's (a linked chart's scroll is the shared time's, and ⌘ over a linked tile zooms it): a burst keeps the meaning its first event gave it, so a page scroll that reaches the end never turns into a pan of the time. A click on the chip opens `T`'s menu, and on the live status runs the commands again (`R`). `G` on a dashboard follows the newest again. `?` shows a dashboard's keys.

**The detail panel.** `⏎` opens it for what the cursor is on: a chart's moment (its x in full, each series' value there, a stack's total, the row's other columns), a bar's band, a heatmap's cell, a graph's node (its id, label, group, degree, its fields, its neighbours, each naming its node, its metadata and `fig` block, nested values as folded branches) or edge (its label, weight and fields, and its two ends), a gantt's task (its dates, its fields, and the tasks before and after it). It sits at the figure's right, about a third of its width (at the bottom of a window under 560 px wide), on a ground a step off the figure's, and the figure lays out in what's left, so nothing hides under it. `⏎` again or `Esc` closes it. It follows the cursor and the data while it's open. `Tab` gives it the keys and `S-Tab` gives them back; with the keys, `j` `k` move between rows, `h` `l` fold and unfold a branch (or go up to it, or into it), `gg` `G` go to the first and last row, `y` `Y` copy, and `⏎` on a row that names a mark (a series' value, a neighbour, an edge's end, a table node's parent, a task another comes after) takes the figure's cursor there, the panel following it; on the value the cursor is on already it shows that series' own tree (its count, least, most, mean and last), whose rows go back to their points. The pointer: a row that names a mark brings it forward in the figure, a click moves the panel's cursor and gives it the keys and a click in the figure gives them back, the fold triangle or a double click folds a branch, a double click on a row that names a mark goes there, and the wheel scrolls the panel. A grouped bar's band lists its parts with no total (a stack's has one), and a table's node says its name once and its parent by name. On a chart the cursor's card goes while the panel shows the same values (a hover's stays); the figure keeps the window's margins, so nothing moves as the panel opens, and at the bottom of a small window a chart drops its legend, its axes' titles and then its title before its plot gets too short to read. `?` shows a graph's keys on a graph, and a gantt's on a gantt.

**The pointer**, as a dashboard's. Hover needs no click and no focus and has no delay: the crosshair follows every sample the pointer sends (not a cell at a time) and snaps to the nearest sample, a dot rings each series' value there, one card lists every series' value at that x, values first, the series nearest the pointer comes forward while the others fade a little and its row in the card is marked, and a bar under the pointer lifts. The series brought forward stays forward while the pointer stays near its line, so a hand trembling over dense data doesn't flicker it. A legend key under the pointer is underlined and brings its series forward. An axis's labels light faintly under the pointer, and on a bar chart a category's label is its band: hovering it lifts the band and a click puts the cursor there. Everything clears when the pointer leaves the figure, for another window, a margin, the command line or another app. A move redraws only what changed in the overlay: the old and new crosshair, dots and card, not the chart under them. A click puts the cursor on the nearest sample; ⇧-click sets the reference there, moves it, or clears it on itself (on a time chart, anywhere on its moment). A left drag on the plot is a brush: a band across a time chart, a box on a scatter, whole bands on a bar chart; ⌘-drag is a box on a time chart too, which sets y by hand, and ⇧ holds a box to its longer side. Letting go zooms to it, eased, one undo step, and `Esc` mid-drag drops it. While a brush is drawn the view holds still: live data arrives and draws, but nothing slides under the hand. ⌥-drag or a middle drag pans, following the hand and never eased; a drag on an axis's labels pans that axis alone. The wheel pans, down and right both moving later on a time chart (and on along a bar chart's bands) so a plain mouse wheel works, by whole pixels with what's left over kept for the next; over an axis's labels it pans that axis alone, and once y is set by hand it pans both ways, as on a scatter. ⌘ (or Ctrl) with the wheel zooms about the pointer, the value under it staying under it, and over an axis only that axis. A burst of scrolling keeps the meaning of its first event, so trackpad momentum never turns into a zoom when ⌘ goes down mid-flick, and the burst is one undo step. A double click resets the view, or on an axis that axis. On the legend a click hides or shows a series, ⌥-click shows only it (again: all), and a double click shows only it, as one undo step. The press that gives the window the focus only focuses it, as on a board. The right button, Space and Ctrl-click open nothing: Ctrl-click is a click. A second button mid-drag ends nothing and starts nothing; a key or the focus going mid-pan ends it where it stands, logged for `u`. When the view moves under a still pointer (the wheel, an ease, live data) the hover snaps again from where the pointer rests.

**When it can't draw.** A figure that has never drawn (its file or data missing, JSON or CSV that doesn't parse, a field the data hasn't, text where the spec says numbers, no rows) shows the error figure in its place: centred and quiet, a muted outline glyph for the kind (a document with a question mark when the text couldn't be read, a document with a squiggled line when it doesn't parse, two pieces that don't fit when the data doesn't fit the spec, empty dashed bars when there's nothing to draw), the status as an icon and a word (red for the first three, amber for nothing to draw), `Can't draw NAME` or `Nothing to draw in NAME`, the first error with its place (`line 4, column 43: expected ',' or '}'`, or the data file's), and `! details · \v source`. A smaller window drops the hint, then the message's second line, then the message and the title (the glyph and its status, which still says it's a failure), then shows the glyph alone, then the title alone. A filter that keeps no row is nothing to draw too, and a command that ran and printed nothing says so. With every series hidden, the chart keeps its legend and axes and shows the empty glyph in the plot: `Every series is hidden`, `X shows them all · or click a key`. `!` or a click turns it over to the log: every error and warning of that build in the monospace, as rustc writes them, the kind and the message, `--> file:line:column`, the source line with a caret under the column, and what was tried (the file read and how many rows it had, the columns it has, where a missing file was looked for, a command's exit status and the end of what it wrote to stderr). The entry under the pointer or moved to with `j` `k` is lit; `<CR>` or a double click goes to its line and column in the source, or in the data file (a number column's text goes to the very cell), shown in this window as `\v` shows the source. A click on the log's header, `!` or `Esc` turns it back. Errors go to the messages too, a run of the same one once.

**Live data.** A figure follows its source as you edit it: once the buffer has been quiet 150 ms the text is read again in a job, and the chart changes. A data file the spec names is read from its buffer when one visits it, following its edits unsaved; otherwise from disk, its modification time looked at once a second while a window shows the figure. If a build fails once the figure has drawn, the last chart stays, so nothing flashes while you type, and a badge in its top-right corner says `Error · line 14` (`Error · latency.csv, line 6` for a data file's); where that would cover the title, the legend or a label it says less (the line alone, the word, the icon), cutting a long title back to make room or, at the smallest, going into the plot's corner as the icon; a click on it brings the log up over the chart, and the badge goes as soon as the source parses again. A spec's data can come from a command: `{"run": "./errors.sh", "every": "30s"}` runs it in the spec's directory (when the figure opens, each 30 s, and on `R`, one run at a time) and reads what it prints as a file would be read; `{"stream": "./ticker.sh"}` starts it once and makes a row of each line it prints, folded in at most 30 times a second, the newest 200,000 kept. Before a command runs, die-fig asks, naming it: `Run "./errors.sh" every 30s for health.fig? (y/n)`, one question at a time and never over a prompt you're typing in; a yes is kept by the spec's path and the command (a restart doesn't ask again), and a no for this session, shown where its data would be as `not run: you said no` until `R` asks again (that figure's questions only). A command named by two of a dashboard's sources (another `every`, another format) runs for each, one yes for both. A dashboard's `file` panel, or a `x.fig#name` borrow, outside its spec's directory (by `..` or a link out too) asks the same way before it's read, and a no shows `not opened: you said no`. `:fig !cmd`, which you type, asks nothing. A figure waits quietly for a command's first output (`waiting for ./ticker.sh`), never dims while a run goes, and keeps its last good data with the badge when one fails, the log saying its exit status and the end of its stderr. Commands run only while a window shows the figure, in a process group each, stopped (SIGTERM, then SIGKILL a second later) when no window does any more and when DIE quits, and their timer runs only while one is due or a stream is open. `G` on a zoomed view follows the newest sample: new data slides the view along. A pan or zoom that leaves the newest off screen stops following, and panning back until the newest is at the right edge starts it again; new data never moves a view that isn't following, nor the cursor off its sample. The status line says `following` while it does, and what the commands are doing (`updating…`, `stream ended (exit 0)`).

**On screen.** Each window showing a figure has two pixel buffers the size of its area: the chart, opaque on the theme's background, and over it the overlay (crosshair, dots, card, brush, emphasis), transparent. The chart is drawn again when the data, the view, the size, the scale or the theme change; the overlay when what it shows does. Both grow with the area and never shrink; a window that closes or shows something else frees its own. Two windows on one figure have a view, cursor and hover each. Eases draw on a 16 ms timer that runs only while something moves; at rest nothing of fig's runs. Faces: `fig-series-1` to `-8` (left unstyled, so the validated dark or light set applies), `fig-good`, `fig-warning`, `fig-serious`, `fig-critical`, and the chrome `fig-grid`, `fig-baseline`, `fig-tick`, `fig-text`, `fig-strong`, `fig-tooltip`, `fig-ring` and `fig-cursor`, which mono-dark styles in its greys.

**After `:rebuild`** each figure comes back by its source (the buffer, the file, the `:fig !cmd` command, with what it printed, which is charted again and not run again; one that printed more than 256 KB doesn't come back) with its view: the domains, what's hidden or shown alone, and the cursor, and a graph's pinned nodes, its layout and labels as `s` left them, a gantt's time, rows and settings as `s` left them, and the detail panel if it was open; a dashboard with its time (following the newest still if it was), the focused panel, a panel shown full size, the scroll, and each panel's own view and cursor; your yeses to commands come back too; the one this window showed is shown in it, and the rest wait to be read until a window shows them. Each file comes back as you last looked at it: a `.fig` you left as text opens as text, one you left as its figure as its figure. A selection's figure doesn't come back, nor the reference, the undo history or a log left up.

**Options**, as your config sets them: `fonts` (where DIE's own fonts are, which fill in where the system has none; DIE's own rule by default), and `open_fig_as` (how a `.fig` or `.fig.json` file opens: `Figure`, the default, which your config names, or `Text`). Times without an offset are in the system's zone. Nothing of fig's runs until `\v` or a figure's file.
